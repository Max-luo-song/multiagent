# BEV Condition → Nexus → 3DGS 场景：技术路线详解

这条路线的目标是：给定道路、车辆历史和需要发生的事件，生成车辆之间的后续交互，再把这些运动放进三维场景中，输出不同视角的视频。

理解它要抓住两件事：**Nexus 解决“车怎么动”，三维高斯背景和车辆资产解决“环境与车长什么样”。两者通过车辆在每个时刻的三维位姿连接起来。**

全文用同一个例子解释：A 车从旁边车道切入 B 车前方，B 车作出反应，后方 C 车也可能受到影响。这里 B 是自车。

## 1. 先看清整条路线

整套流程有两条分支，最终汇合到渲染器：

```text
运动分支                                  外观分支

BEV 条件                                  真实场景数据 / 已有三维资产
道路 + 车辆历史 + A 车切入约束              图像、标定、点云 / 背景和车辆模型
        │                                          │
        ▼                                          ▼
Nexus 条件生成                            准备静态背景和独立车辆高斯
得到 A、B、C 的时序状态                    得到环境与车辆的几何、外观
        │                                          │
        ▼                                          │
轨迹坐标对齐 + 高度与姿态补全                       │
得到每辆车每一帧的三维位姿                          │
        │                                          │
        └─────────────────┬────────────────────────┘
                          ▼
                 按三维位姿摆放车辆高斯
                          │
                          ▼
                 设置相机并进行 3DGS 渲染
                          │
                          ▼
                 可回放动态场景与多视角视频
```

这不是把一张俯视图直接“拉高”成三维。BEV 通常只描述平面上的道路和交通状态，没有完整的建筑纹理、车辆外形、路面高度和遮挡区域信息。因此，要生成可观看的三维画面，必须同时准备外观分支。

| 阶段 | 输入 | 输出 |
| --- | --- | --- |
| 组织条件 | 道路、车辆历史、事件要求 | Nexus 可读取的状态张量和条件掩码 |
| 生成运动 | 条件张量、地图、随机噪声 | 多车未来位置、朝向和速度 |
| 转成三维 | BEV 轨迹、坐标关系、路面信息 | 每辆车随时间变化的三维位姿 |
| 驱动资产 | 三维位姿、车辆高斯、背景高斯 | 每个时刻的三维场景状态 |
| 渲染 | 三维场景、相机参数 | 连续图像和视频 |

## 2. BEV condition 到底包含什么，怎样送给 Nexus

### 2.1 BEV 是从上方描述交通状态

BEV 即鸟瞰表示。我们关心的是：路在哪里、车在哪里、朝哪个方向、以什么速度行驶，以及哪些状态已经给定。

当前 Nexus 入口采用结构化数值，主要包括两部分：

- **道路信息：** 车道中心线、边界及相关地图特征，描述车辆可行驶的空间。
- **车辆信息：** 每辆车在多个时间点的位置、朝向、速度和尺寸。

车辆在一个时刻可表示为：

```text
[x, y, cos(yaw), sin(yaw), vx, vy, length, width]
```

`x、y` 是平面位置；`yaw` 是车头方向；`vx、vy` 是两个方向的速度；`length、width` 是车长和车宽。用航向的正弦、余弦表示方向，可以避免角度在 −π 与 π 之间跳变。

把“车辆 × 时间 × 状态”排列起来，就得到状态张量。模型接口还包含一个批次维度，可写成 `[B, N, T, 8]`：B 个场景、每场景 N 辆车、每辆车 T 个时间点、每点 8 个数。

这里最重要的是：**模型输入是一段带时间的交通状态，不只是当前时刻的几个车辆框。** 历史信息帮助模型判断车辆正在加速、减速还是变道。如果只有一张 BEV 图片，需要先识别地图和车辆、确定像素与米的关系，并补充历史或速度估计。

### 2.2 条件掩码决定哪些内容固定、哪些需要生成

可以把状态张量理解成一张待填表格。条件掩码就是标明“这一格已经给定，请保留；那一格未知，请生成”。

切入例子的条件可以这样组织：

| 车辆 | 历史状态 | 未来状态 | 谁决定未来 |
| --- | --- | --- | --- |
| A：事件车 | 已知并固定 | 给定连续的切入轨迹 | 事件条件 |
| B：自车 | 已知并固定 | 待生成 | Nexus，必要时加入引导 |
| C：后车 | 已知并固定 | 待生成 | Nexus，必要时加入引导 |

模型因此接收到的是：“过去大家这样开，接下来 A 将这样切入，请生成 B、C 的后续运动。”

条件掩码与有效性掩码要区分：**条件掩码表示状态是否已知，有效性掩码表示该车辆在该时刻是否存在、是否参与建模。** B 的未来未知，不代表 B 在未来消失。

进入模型前，还要统一坐标、单位和训练时使用的归一化方式；输出给渲染器前再恢复为米、秒等物理量。否则，即使轨迹形状看起来合理，也可能出现尺度错误。

### 2.3 “指定切入行为”怎样变成可用条件

在这条实现路线里，“A 在 3 秒时切入”需要先编译成一段连续运动：A 从原车道出发，逐渐产生横向位移，调整朝向，最后进入 B 所在车道。位置、速度与航向应相互一致，不能在指定时刻突然从一条车道跳到另一条车道。

编译后，A 在各个未来时刻的数值状态被放入条件张量并固定，其余车辆未来留给模型生成。仅写一句动作名称，还没有完成这一步。

## 3. Nexus 怎样把条件变成多车未来轨迹

### 3.1 它生成的是交通状态序列

Nexus 的条件采样可以直观理解为“逐步把未知的未来补充完整”：

1. 编码道路和已知状态，获得当前交通环境的表示。
2. 为待生成的未来部分引入随机噪声，作为采样起点。
3. 通过多轮迭代，在道路、历史及固定事件轨迹的条件下逐步生成未来状态。
4. 保留给定条件，输出参与车辆的完整状态序列。

这里的噪声作用于交通状态的生成过程，与图像上的噪点无关。不同随机种子可以产生不同的未来候选，但不能保证每个候选都合理。

生成结果可理解为如下表格。数值仅用于说明数据形式：

| 时间 | 车辆 | x/m | y/m | 航向 | 速度/m·s⁻¹ |
| --- | --- | --- | --- | --- | --- |
| 0.0 s | B | 0.0 | 0.0 | 沿车道 | 10.0 |
| 0.5 s | B | 4.9 | 0.0 | 沿车道 | 9.6 |
| 1.0 s | B | 9.4 | 0.0 | 沿车道 | 8.4 |

此时我们拿到的是数值化运动，尚未生成车辆纹理或三维高斯。

### 3.2 多车交互是怎样体现的

A 的给定轨迹改变了 B 前方的空间和相对运动关系。Nexus 在多车联合条件下生成未来，因而有机会得到 B 减速、C 随之调整运动的结果。若 C 旁边有可用车道，也可能考虑变道响应。

“联合生成”表示各车未来在同一个交通条件下建模，不能理解为把几条互不相关的单车轨迹拼接起来。但它也不保证一定发生我们希望看到的交互。要确认存在影响，需要看切入前后的距离、相对速度及响应时序，必要时与无事件条件下的生成结果比较。

### 3.3 为什么还需要物理约束或行为引导

学习模型给出的是可能的运动，可能出现碰撞、越界、急转或不合理加速。因此，生成阶段可以加入道路、车间距离、加速度、曲率等约束，限制不合理状态。

如果要求明确的停车或变道行为，还可以加入停车目标、目标车道等意图引导。此时轨迹由“模型生成 + 约束/引导”共同决定。要区分**给模型一个目标**与**直接固定完整未来轨迹**：前者仍需要生成达到目标的连续运动，后者已经把运动指定好了。

如果不希望车辆提前知道未来事件，可以先执行正常片段，等事件触发后，用截至此时的已执行历史和新条件重新生成剩余轨迹。这属于事件触发重规划。

本阶段的输出是带稳定车辆 ID、时间戳、位置、朝向、速度和尺寸的轨迹。进入三维转换前，应检查车身重叠、道路越界及速度/姿态连续性；渲染器本身不会修复错误运动。

## 4. 三维背景与车辆高斯从哪里来

这一步可以与轨迹生成并行进行。首先要理解 3DGS 表示什么。

### 4.1 三维高斯可以理解成带外观的空间椭球

普通点只有位置；三维高斯还描述该位置周围的空间范围，可直观理解成一个具有方向、大小、颜色和透明度的柔和椭球。

大量高斯共同表示路面、建筑、树木或车辆。相机从某个方向观察时，渲染器将这些高斯投影到图像上并合成，得到可见画面。

单个高斯的关键参数包括：

- 中心：它在三维空间的哪里。
- 尺度和旋转：它沿哪些方向展开、范围多大。
- 不透明度：它对画面的遮挡贡献有多大。
- 外观系数：它从不同观察方向呈现什么颜色。

### 4.2 场景要能区分背景和可移动对象

为了编辑车辆运动，需要把场景组织为两类：

```text
静态背景：道路、建筑等 → 固定在场景坐标系中
动态车辆：A、B、C 各自的高斯集合 → 在车辆局部坐标系中保存
```

车辆局部坐标系随车移动，因此同一份车辆资产可以在不同位置重复使用，也可以沿新轨迹运动。若车辆已经不可分离地融合进背景，直接插入一辆新车会留下原车影像；需要先分离对应对象或处理原车区域。

### 4.3 准备外观有两条途径

**原场景重建：** 用同一场景的多视角图像、相机标定和位姿，结合可用点云及动态对象标注，重建静态背景和独立车辆高斯。渲染与实际观测的差异用于优化高斯参数，使原相机下的画面接近真实图像。得到可编辑表示后，再替换车辆运动。

**复用已有资产：** 直接加载已有道路背景高斯和车辆高斯 PLY。省去重新重建，但要校准尺寸、朝向和道路位置，并确认背景道路支持目标行为。普通点云或网格文件不能仅因扩展名为 PLY 就直接当作完整车辆高斯，必须检查其参数格式。

这两条途径都提供三维几何和外观。Nexus 生成的轨迹用来驱动它们，不需要每次修改运动都重新训练背景。

## 5. 怎样把 BEV 轨迹变成三维车辆位姿

这是连接运动与外观的核心。**位姿 = 位置 + 朝向**：不仅要知道车在哪里，还要知道车头朝哪、车身是否随坡面倾斜。

### 5.1 对齐坐标：让轨迹落在正确的道路上

Nexus 通常在自车局部坐标系里生成运动，而三维背景保存在另一个坐标系中。两个坐标系的原点和方向可能不同，因此相同的 `(x, y)` 数值并不指向同一个地点。

例如，Nexus 中 B 位于 `(0, 0)`，三维背景中的对应起点可能在 `(100, 50)`，且道路朝向相差 90°。需要先旋转，再平移，才能将轨迹放到背景道路上。

若两者对应同一米制场景，这种关系可以写成：

```text
p_scene = R_align · p_nexus + t_align
```

`R_align` 是两个坐标系的方向差，`t_align` 是原点偏移。航向也要同步旋转。存在地图世界坐标时，可以通过“局部 → 世界 → 三维场景”的坐标链完成转换。

若换成另一条形状不同的道路，单一旋转和平移可能不够。可以先把轨迹表示为“沿车道前进的距离 s + 相对车道中心的横向距离 d”，再映射到目标车道；这称为沿车道的 Frenet 映射。前提是道路方向、车道连接和可用空间相容，否则必须重新生成运动。

### 5.2 补齐高度与坡度：让车真正落在路面上

BEV 主要给出平面位置和航向，缺少路面高度、车辆俯仰和侧倾。需要查询三维路面或由点云估计：

```text
平面位置 (x, y) → 对应路面高度 z_ground
路面法向 + 车辆航向 → 车身三维旋转 R
资产底部与路面关系 → 车辆参考点高度
```

如果车辆资产原点在车身中心，就需要将中心抬高，使轮胎底部接近地面；如果原点本来就在接地点，则不能重复抬高。坡道上还需调整俯仰和侧倾，否则车辆会悬空或插入路面。

同时，要统一运动状态的参考点。自车轨迹可能使用后轴中心，车辆资产可能使用车身中心；必须按车长和车型参数换算，不能直接把两点当成同一点。

### 5.3 对齐时间：从轨迹采样点得到视频帧

轨迹时间间隔不一定等于视频帧间隔。例如，轨迹每 0.5 秒一个状态，视频按 10 帧/秒渲染，就需要每 0.1 秒得到一个位姿。

通过位置插值和连续角度/旋转插值，补出中间状态，避免车辆一跳一跳地移动。航向跨过 ±π 时要按连续旋转处理；插值使显示更连续，但不能修复原轨迹中的碰撞或不合理加速。

最终，每辆车在每个渲染时刻都有一个变换：

```text
T_scene←vehicle(t) = [R(t), p(t)]
```

它的意思是：将车辆自身坐标中的点，旋转并平移到三维场景中的正确位置。

## 6. 车辆高斯怎样随轨迹运动

### 6.1 先把车辆 ID 与资产绑定

为 A、B、C 各绑定一份车辆高斯资产，并校准长度、宽度、朝向及局部原点。这个绑定在整个视频中保持一致，避免不同帧换车或错配身份。

需要缩放时，不仅调整高斯中心，还要同步调整高斯的空间尺度。仅改变显示框大小不会改变实际车辆外形。

### 6.2 每帧对车辆的全部高斯做刚体变换

车辆资产可以看作一组装在车身上的高斯。车往前移动，整组一起平移；车转向，整组围绕车辆参考点旋转，无需重新生成车身。

对某个局部高斯，变换公式为：

```text
μ_scene(t) = R(t) · μ_local + p(t)
Σ_scene(t) = R(t) · Σ_local · R(t)ᵀ
```

第一行移动高斯中心 `μ`。第二行旋转协方差 `Σ`，也就是旋转高斯椭球的展开方向。若只移动中心而不旋转椭球，车辆转弯时外形就可能出错。

外观还可能随观察方向变化，因此车辆旋转后也应按一致的局部观察方向计算颜色。

在切入例子中，A 的整组高斯从相邻车道进入 B 前方；B、C 的高斯按各自生成的轨迹移动。三辆车的状态可以同时更新，而道路背景固定。至此，每个时刻的三维场景都已确定，只差选择相机进行观察。

## 7. 怎样从动态高斯场景得到多视角视频

### 7.1 相机决定从哪里看、能看多宽

相机需要两类参数：

- **内参：** 焦距、主点等，决定三维内容如何投影到图像上。
- **外参：** 相机在场景中的位置与朝向，决定观察方向。

路侧相机可以固定不动；跟随相机根据某辆车的位置更新；自车相机则固定安装在 B 车上，随 B 一起移动：

```text
T_scene←camera(t)
  = T_scene←B(t) · T_B←camera
```

右侧第二项表示相机相对 B 车的固定安装位置，第一项表示 B 在场景中的逐帧位姿。两者相乘，就得到相机逐帧位姿。

### 7.2 渲染器把同一时刻的三维高斯合成为图像

对每一个视频时刻，执行：

1. 查询 A、B、C 的三维位姿，更新各车高斯。
2. 将车辆高斯与静态背景放在同一场景坐标系中。
3. 将高斯变换到相机坐标，并投影到图像平面；三维椭球形成二维椭圆状贡献。
4. 根据深度和不透明度合成颜色，得到一帧图像。
5. 对后续时刻重复，再按帧率编码为视频。

因为背景和车辆共同参与三维渲染，A 挡住 B、车辆被路侧物体遮挡等关系，可以通过空间深度体现。

### 7.3 多视角共用同一段运动

要同时输出 B 的前视、C 的前视和外部观察视角，只需为同一组场景状态设置多个相机，分别渲染。**更换观察视角不需要重新调用 Nexus，否则不同视频可能对应不同的运动。**

换视角也受重建覆盖限制：如果新相机看到原始数据未充分观测的车背面、路面或建筑区域，就可能出现模糊或缺失。车辆外观问题需要补车辆资产，背景问题需要补背景观测或重建。

最终建议保存的结果包括背景/资产文件引用、车辆 ID 与资产绑定、逐帧三维位姿、相机参数，以及渲染视频。视频是一次观察结果，前面的数据才使场景可以换视角、重新渲染和复用。

## 8. 可以怎样向别人讲清楚

> 我们先把 BEV 中的道路、车辆历史和事件要求整理成 Nexus 的条件输入。通过条件掩码，固定事件车的运动，让 Nexus 生成自车和其他车辆的后续交互，并用道路与运动学约束检查或引导结果。
>
> 得到的轨迹还是平面上的数值状态，所以接下来要把它对齐到三维背景，补充路面高度、坡度和车辆参考点关系，得到每一帧的三维位姿。同时准备静态背景高斯和独立车辆高斯资产，再用这些位姿驱动车辆资产运动。
>
> 最后设置相机，把背景和动态车辆放进同一个 3DGS 渲染器，生成图像和视频。多个相机共用同一段车辆运动，就能得到同步的多视角结果。整个过程里，Nexus 负责生成交互运动，三维高斯负责表示与渲染几何和外观，两者通过时序位姿连接起来。
